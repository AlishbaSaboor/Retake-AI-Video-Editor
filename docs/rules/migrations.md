# Migrations

**The generator writes the migration. You write the schema.**

- Never create or edit files under `prisma/schema/migrations/` by hand —
  every file there is generated by `scripts/generate-migration.mjs`.
- Change `prisma/schema/*.prisma`, run `pnpm prisma:generate`, then
  generate the migration against your local database with every committed
  migration applied:
  `pnpm exec prisma migrate deploy`, then
  `node scripts/generate-migration.mjs --name <short_name> --db-url <local url>`.
  It diffs the replayed history against your schema and writes the missing
  migration. Apply it (`pnpm exec prisma migrate deploy` again) and commit
  it with the schema change.
- **If the generator refuses (exit 2)**, `prisma migrate diff` emitted a
  destructive pattern like `DROP COLUMN`/`SET NOT NULL`, which needs
  hand-written data-preserving SQL via `prisma migrate dev --create-only`
  instead — the one sanctioned exception to "never hand-write a migration".
- The other sanctioned hand-written migration is
  `ALTER TABLE "<table>" ENABLE ROW LEVEL SECURITY;` for each new table —
  the Prisma schema can't express it (`docs/rules/auth.md`), and
  `pnpm check:rls` stays red until it exists. Nothing else in the file: no
  policies, never `FORCE`.
- Run `node scripts/generate-migration.mjs --check --db-url <url>` to
  preview what would be generated without writing it.
- **The `migrations` job** (`.github/workflows/manual.yml`, run by hand from
  the Actions tab) replays the committed migrations onto a clean Postgres,
  applies `prisma/run-once.sql`, fails on any drift from the schema, and
  runs `pnpm check:rls`. It only checks; it never writes a migration. Run it
  on a branch that changes the schema before merging.
- No SQL-editor writes against staging or production, ever, for schema or
  data. One-off data fixes go in `prisma/run-once.sql` (next section).
- Nothing applies migrations to the hosted Supabase database
  automatically: apply them before the deploy that needs them, with
  `DIRECT_URL` set to the session pooler (`docs/rules/deployment.md`).
  `pnpm exec prisma migrate deploy` applies them to your local one.

## Run-once SQL — `prisma/run-once.sql`

The one SQL file outside `migrations/` that you hand-write. Whatever it
holds runs **once per database**: the manual `migrations` job applies it to a
throwaway Postgres right after `prisma migrate deploy`, and
`pnpm db:run-once` applies it to your local database. It is for one-off changes that aren't a schema change — fix a value,
insert reference rows, backfill a column, replace a view, add an extension
or a grant.

**Using it.** Replace the file's content with the new one-off (don't append
to the last one — it already ran), test it with `pnpm db:run-once` against a
local database, run the manual `migrations` job on the branch, merge. It
applies the file to a throwaway Postgres, so a one-off that is broken, or
that depends on rows only production has, fails there first.

**How "once" works.** `scripts/run-once-sql.mjs` hashes the file's
executable content — comments and whitespace don't count, so a doc tweak
never re-runs anything — and skips any version already recorded in the
`_run_once_sql` ledger (`prisma/schema/run-once-sql.prisma`). The ledger row
and the SQL go to Postgres as one command, in one implicit transaction: both
land or neither does, so a failed run is retried on the next deploy and a
successful one cannot repeat. Query the ledger to see what has run where and
when. To run the same SQL again on purpose, a statement has to change; a
comment won't do it.

- **Not a schema side-channel.** Tables, columns, indexes, and enums belong
  in `prisma/schema/*.prisma` — the drift check that runs right after this
  file fails if it created anything Prisma tracks.
- **The `migrations` job applies it to an empty database first.** Write it so that matching
  nothing is fine (an `UPDATE ... WHERE` that finds no rows), and guard an
  `INSERT` that needs rows only production has
  (`INSERT ... SELECT ... WHERE EXISTS`).
- **One transaction.** Nothing that refuses to run inside a transaction
  block (`CREATE INDEX CONCURRENTLY`, `VACUUM`).
- **Merge conflict in this file? Keep only your SQL.** The other side's
  version was applied under its own hash; keeping both makes a new version
  that runs the old one-off again.
- On production the order is migrations → this file → drift check, all in
  one job, so the file may use a table the same PR's migration creates. The
  app-deploy ordering caveat above applies here too.

Note: this repo uses the Prisma schema only; the Supabase-CLI migration
workflow (`supabase migration new`, `NOTIFY pgrst`) does not apply here.

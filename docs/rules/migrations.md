# Migrations

**CI writes the migration. You write the schema.**

- Never create or edit files under `prisma/schema/migrations/` by hand —
  every file there is generated by `.github/workflows/ci.yml`'s
  `migrations` job, via `scripts/generate-migration.mjs`.
- Your job stops at `prisma/schema/*.prisma` and application code. Change
  those, run `pnpm prisma:generate`, make the gates pass, push. CI replays
  the committed migrations onto a clean Postgres, diffs it against your
  schema, writes the missing migration, replays that too to prove it
  applies, and commits it back to your branch.
- **A red `migrations` check is real.** Either the generator refused (exit
  2 — `prisma migrate diff` emitted a destructive pattern like `DROP
COLUMN`/`SET NOT NULL`, which needs hand-written data-preserving SQL via
  `prisma migrate dev --create-only` instead — the one sanctioned exception
  to "never hand-write a migration"), or a push to `main` drifted (red
  there means a schema change reached `main` without its migration).
- The other sanctioned hand-written migration is
  `ALTER TABLE "<table>" ENABLE ROW LEVEL SECURITY;` for each new table —
  the Prisma schema can't express it (`docs/rules/auth.md`), and
  `pnpm check:rls` at the end of the `migrations` job stays red until it
  exists. Nothing else in the file: no policies, never `FORCE`.
- Run `node scripts/generate-migration.mjs --check --db-url <url>` to
  preview what CI would generate without writing it.
- Pull before you keep working — the generated commit lands on your branch.
- No SQL-editor writes against staging or production, ever, for schema or
  data. One-off data fixes go in `prisma/run-once.sql` (next section),
  through the same PR/CI path.
- `.github/workflows/deploy-migrations.yml` applies migrations to
  production on every push to `main`, then runs `prisma/run-once.sql` (next
  section). Flag deploy _ordering_ when a query depends on a new column —
  app deploy and the migration job aren't guaranteed to be sequenced yet.

## Run-once SQL — `prisma/run-once.sql`

The one SQL file outside `migrations/` that you hand-write. Whatever it
holds runs **once per database**, on the next deploy: `deploy-migrations.yml` applies it to
production right after `prisma migrate deploy` and before the zero-drift
check. It is for one-off changes that aren't a schema change — fix a value,
insert reference rows, backfill a column, replace a view, add an extension
or a grant.

**Using it.** Replace the file's content with the new one-off (don't append
to the last one — it already ran), test it with `pnpm db:run-once` against a
local database, open the PR, merge. `ci.yml`'s `migrations` job applies the
file to its throwaway Postgres on every PR, so a one-off that is broken, or
that depends on rows only production has, fails there first.

**How "once" works.** `scripts/run-once-sql.mjs` hashes the file's
executable content — comments and whitespace don't count, so a doc tweak
never re-runs anything — and skips any version already recorded in the
`_run_once_sql` ledger (`prisma/schema/run-once-sql.prisma`). The ledger row
and the SQL go to Postgres as one command, in one implicit transaction: both
land or neither does, so a failed run is retried on the next deploy and a
successful one cannot repeat. Query the ledger to see what has run where and
when. To run the same SQL again on purpose, a statement has to change; a
comment won't do it.

- **Not a schema side-channel.** Tables, columns, indexes, and enums belong
  in `prisma/schema/*.prisma` — the drift check that runs right after this
  file fails if it created anything Prisma tracks.
- **CI applies it to an empty database first.** Write it so that matching
  nothing is fine (an `UPDATE ... WHERE` that finds no rows), and guard an
  `INSERT` that needs rows only production has
  (`INSERT ... SELECT ... WHERE EXISTS`).
- **One transaction.** Nothing that refuses to run inside a transaction
  block (`CREATE INDEX CONCURRENTLY`, `VACUUM`).
- **Merge conflict in this file? Keep only your SQL.** The other side's
  version was applied under its own hash; keeping both makes a new version
  that runs the old one-off again.
- On production the order is migrations → this file → drift check, all in
  one job, so the file may use a table the same PR's migration creates. The
  app-deploy ordering caveat above applies here too.

Note: this repo's Prisma-schema-only workflow is a deliberate, different
choice from the Supabase-CLI workflow used elsewhere in the org
(`supabase migration new`, `NOTIFY pgrst`) — those conventions do not
apply here. See the design guide's "central decision" section for why
Prisma's CI-generated model was chosen over the Supabase-CLI alternative.

See `docs/CI_CD_SETUP.md` for what GitHub secrets this workflow needs
(`MIGRATIONS_TOKEN`, the `production-database` environment) before it works
end to end.

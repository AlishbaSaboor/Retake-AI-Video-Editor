## On auth: don't send a secret to MOAD at all

Your framing assumes each project generates a secret and you then have to get it into MOAD safely. Flip the direction and the distribution problem disappears.

MOAD holds one Ed25519 private key. It signs each request. Every project verifies with MOAD's **public** key, which is not a secret, so it ships in the template's `.env.example` as a committed default. A new repo from the template needs zero credential provisioning. Nothing to paste, nothing to leak from the app side, nothing sitting in a Vercel env var for N repos.

Sits right next to `createCronRoute` in `src/server/api/route-factory.ts`, no new dependency:

```ts
import { verify, createPublicKey } from 'node:crypto'

const moadKey = createPublicKey(env.MOAD_PUBLIC_KEY) // SPKI PEM, not secret

export function createMoadRoute(handler: (req: NextRequest) => Promise<Response>) {
	return async function (req: NextRequest) {
		const [ts, sig] = (req.headers.get('x-moad-signature') ?? '').split('.')
		const fresh = Math.abs(Date.now() - Number(ts)) < 60_000
		const ok =
			fresh &&
			verify(null, Buffer.from(`${ts}:${env.MOAD_AUDIENCE}`), moadKey, Buffer.from(sig, 'base64url'))
		if (!ok) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
		return handler(req)
	}
}
```

`MOAD_AUDIENCE` is the project slug, so a signature minted for project A can't be replayed against project B. The 60s window kills replay. Rotation is a new public key in the template plus a redeploy, or a JWKS URL if that ever gets annoying enough to matter.

Why not the alternatives:

- **Per-project shared bearer secret** (the `CRON_SECRET` pattern you already have) works, and if you want it, generate it *in MOAD* and paste it straight into Vercel, never through Slack or a ticket. But it's N real credentials living in two places each, and every new repo is another provisioning step someone forgets.
- **HMAC signing with a shared secret** is strictly worse than the bearer token. Same symmetric secret in both places, more code, and TLS already gives you what the signature would.
- **MOAD reading each project's Postgres directly** trades one API for N database credentials and couples MOAD to every schema. Worse on both counts.

Also worth saying: make the endpoint aggregate-only, never expose the `meta` jsonb. Then the blast radius of any auth failure is a spend number, not `user_id`s.

## Three things I'd change in the design itself

**Compute cost at write time, not read time.** If the API prices at query time from live OpenRouter data, last quarter's reported spend silently changes when a model gets cheaper. Store `cost_usd` on the row alongside the tokens. The read API becomes a pure `SUM`, MOAD stops depending on OpenRouter being up, and history stops drifting.

**The model-id mapping is the actual hard part.** Anthropic serves `claude-opus-4-5-20260101`, OpenRouter calls it `anthropic/claude-opus-4.8`. You need an explicit lookup with a loud failure on unknown models, otherwise a new model quietly costs $0 forever and nobody notices for a month.

**Never let a tracking insert fail the AI call.** Wrap the write in Next 16's `after()` so it runs post-response and a dead DB costs you a row, not a user-facing error.

On package vs skill: the client is runtime code, so it can't be a skill. Since every project starts from this template, put it in `src/lib/ai-usage/` here and only extract an npm package when you need to push updates into repos that already exist.

| what the provider returns | OpenRouter `id` | its `canonical_slug` |
|---|---|---|
| `claude-opus-5` | `anthropic/claude-opus-5` | `anthropic/claude-opus-5-20260723` |
| `claude-haiku-4-5-20251001` | `anthropic/claude-haiku-4.5` | `anthropic/claude-4.5-haiku-20251001` |
| `claude-sonnet-4-5-20250929` | `anthropic/claude-sonnet-4.5` | `anthropic/claude-4.5-sonnet-20250929` |

Anthropic writes `opus-4-5`, OpenRouter writes `4.5-opus` in the canonical slug and `opus-4.5` in the id. The date matches, the word order doesn't. You could write a normalizer that handles those two shapes, and it would work until Google ships `gemini-3.1-flash-lite-image-preview` and it quietly resolves to the wrong row. A normalizer that's usually right is worse than no normalizer, because being wrong costs you money silently instead of loudly.

So: an explicit map, and it's small. You use maybe eight models, not 425.

```ts
// src/lib/ai-usage/models.ts
// Provider's model id (what the response actually reported) -> OpenRouter slug.
// Add the entry before shipping a call to a new model. Nothing here is
// derived: the two id schemes disagree on word order and separators, and a
// normalizer that guesses wrong mis-prices silently instead of failing.
const OPENROUTER_SLUGS: Record<string, string> = {
	'claude-opus-5': 'anthropic/claude-opus-5',
	'claude-sonnet-5': 'anthropic/claude-sonnet-5',
	'claude-haiku-4-5-20251001': 'anthropic/claude-haiku-4.5',
	'gpt-5.4': 'openai/gpt-5.4',
	'gemini-3.8-flash': 'google/gemini-3.8-flash'
}

export function openRouterSlug(model: string, serviceTier: string): string | null {
	const slug = OPENROUTER_SLUGS[model]
	if (!slug) return null
	// `batch` is a separate upstream entry at half price, not a modifier.
	return serviceTier === 'batch' ? `${slug}:batch` : slug
}
```

## Where it fails loudly

Three places, because each one catches a different way this goes wrong.

**At write time, never by throwing.** An unmapped model writes the row with `cost_usd = null` and calls `captureError` once. Losing the usage row because pricing failed is a much worse outcome than losing the price. Null, not zero: zero is a lie that sums correctly.

**On the daily price refresh, in both directions.** When the job pulls `/api/v1/models`, it checks every slug in your map still exists upstream. Retired slugs are how a mapping rots without anyone touching the code. This replaces the flaky idea of a network-hitting unit test, and it's the job you already need.

**On the dashboard, which is the one that actually works.** Sentry alerts get muted in a week. A number on MOAD's screen doesn't:

```json
{
  "totals": { "cost_usd": 1284.22, "input_tokens": 91_233_412 },
  "by_model": [ ... ],
  "unpriced": [{ "provider": "anthropic", "model": "claude-opus-6", "calls": 3412 }]
}
```

That array is empty in the normal case and impossible to miss when it isn't. It's also the honest answer to "is this number complete", which a bare `cost_usd` never is.

There's no client to import. `trackAiCall` wraps the provider SDK call you were going to write anyway, so you still install and call the SDK yourself. The example below is one I actually typechecked against the real types, not a sketch.

## 1. Install the SDK you need

```bash
pnpm add @anthropic-ai/sdk        # or openai, or @google/genai
```

Then add its API key to `.env.example` and `src/lib/env.ts`, or `pnpm check:env` fails.

## 2. Wrap the call

In a server action or an API handler under `src/server/`:

```ts
import 'server-only'
import Anthropic from '@anthropic-ai/sdk'
import { trackAiCall } from '@/server/lib/ai-usage/sink'

const anthropic = new Anthropic()

export async function writeOfferCopy(brandId: string, prompt: string) {
	const message = await trackAiCall(
		{
			provider: 'anthropic',
			model: 'claude-opus-5',
			feature: 'offer_copy',
			meta: { brand_id: brandId }
		},
		() =>
			anthropic.messages.create({
				model: 'claude-opus-5',
				max_tokens: 1024,
				messages: [{ role: 'user', content: prompt }]
			})
	)

	return message.content[0]?.text
}
```

That's the whole integration. `message` is the real `Anthropic.Message`, fully typed, with autocomplete intact. Errors from the SDK come through unchanged, so your existing try/catch still works. The row is written after your response goes out, so none of this adds latency.

OpenAI and Google are identical apart from the `provider` field:

```ts
await trackAiCall({ provider: 'openai', model: 'gpt-5.4', feature: 'tag_suggestions' }, () =>
	openai.chat.completions.create({ model: 'gpt-5.4', messages })
)
```

## 3. The two fields worth thinking about

**`feature`** is the axis every cost question gets asked along. When someone asks "why did spend triple in March", the answer is a `feature` breakdown or it's nothing. `offer_copy` and `offer_copy_retry` answer different questions; `generate` answers none.

**`model`** only accepts a key from `OPENROUTER_SLUGS`. This won't compile:

```ts
trackAiCall({ provider: 'anthropic', model: 'claude-opus-9', feature: 'x' }, ...)
//                                          ^ not assignable to TrackedModel
```

Add it to `src/server/lib/ai-usage/models.ts` first, taking the `id` field from `https://openrouter.ai/api/v1/models`. That error is the feature, not an obstacle.

**`meta`** takes ids only. `{ brand_id, campaign_id, user_id }`, never prompt or completion text. It's the reason the MOAD endpoint is safe to expose at all.

## 4. Streaming

The extractors read a finished response, so wrap the part that resolves it. The stream still reaches the user immediately:

```ts
const stream = anthropic.messages.stream({ model: 'claude-opus-5', max_tokens: 4096, messages })

// Hand the stream to the caller now; record usage when it finishes.
void trackAiCall({ provider: 'anthropic', model: 'claude-opus-5', feature: 'offer_copy' }, () =>
	stream.finalMessage()
)

return stream.toReadableStream()
```

`finalMessage()` resolves with the accumulated usage once the stream ends.

## 5. Image and embedding endpoints

These report usage in shapes the three built-in extractors don't know, so pass `extract`:

```ts
await trackAiCall(
	{
		provider: 'openai',
		model: 'gpt-5.4',
		feature: 'product_thumbnail',
		extract: response => ({ tokens: { inputTokens: tokensFrom(response), outputTokens: 0, cacheWriteTokens: 0, cacheReadTokens: 0 } })
	},
	() => openai.images.generate({ ... })
)
```

If your extractor throws, the AI call still succeeds and no row is written. There's a test for exactly that.

## What the two things are

**`MOAD_PUBLIC_KEY`** is one half of an Ed25519 keypair. MOAD generates the pair once, keeps the private half, and publishes the public half. The asymmetry is the point: the private key can *create* signatures, the public key can only *check* them. Handing every repo the public key gives them the ability to verify MOAD and nothing else. It can't be used to forge a request, which is why it's committed to `.env.example` rather than treated as a secret.

**`MOAD_AUDIENCE`** is just this project's slug, `8x-brands` or whatever the repo is called. Also not a secret. It exists so a signature is bound to one specific project.

Neither value is a credential. Nothing in the repo can authenticate *as* anyone.

## The flow

MOAD wants to read `8x-brands`. It takes the current time in milliseconds and the target project's slug, joins them into `1788517056488:8x-brands`, and signs that string with its private key:

```
x-moad-signature: 1788517056488.VMLQiJtI7kwwhrrbYRRB5ipRyaPsjHIgLLzYzSgFWQQ...
                  └─ timestamp ─┘ └────────── base64url signature ──────────┘
```

`8x-brands` receives it, rebuilds the same string from the timestamp in the header and **its own** `MOAD_AUDIENCE`, and asks the public key whether that string was signed by the matching private key. That's `createMoadRoute` in `src/server/api/route-factory.ts`, and it's the whole check.

The verification only succeeds if three things hold: the signature was made by MOAD's private key, over a message naming *this* project, less than 60 seconds ago. Live results from the run above:

| | |
|---|---|
| `8x-brands` verifies its own header | ✅ true |
| `8x-marketing` replaying that same header | ❌ false, wrong audience |
| A signature 2 minutes old | ❌ false, outside the window |
| Forged with an attacker's own keypair | ❌ false |
| One byte of the signature altered | ❌ false |

The second row is why the audience is in there. Without it, anyone who intercepted MOAD's request to one project could replay it against every other project and read all their ledgers. The timestamp closes the same hole within a single project.

## Calling it authorization is generous

This is authentication of a single caller. There's one client (MOAD), one permission (read aggregates), no roles and no scopes. That's sized to the problem: the endpoint returns spend numbers, never rows and never `meta`, so there's nothing to grant partial access to. If MOAD ever needs to write, or a second consumer appears, that's the point to add real scopes rather than now.

## The half that doesn't exist yet

MOAD needs to sign. That's four lines, and nobody has written them:

```ts
import { sign } from 'node:crypto'

function moadSignature(projectSlug: string, privateKey: KeyObject) {
	const timestamp = Date.now()
	const signature = sign(null, Buffer.from(`${timestamp}:${projectSlug}`), privateKey)
	return `${timestamp}.${signature.toString('base64url')}`
}
```

`sign(null, ...)` with no digest algorithm is correct for Ed25519, not an omission.

Operationally, MOAD generates the pair once with `generateKeyPairSync('ed25519')`, stores the private key in its own env (this is the only real secret in the whole system, and it lives in exactly one place), and publishes the public PEM. That PEM then gets pasted into each repo's `.env.example` and Vercel config. Per project, MOAD stores only the slug and the base URL.

Rotation: generate a new pair, update `.env.example` across the repos, redeploy. Annoying at ten repos, fine at five. If it becomes annoying enough, MOAD serves the public key at a JWKS URL and projects fetch it, but that's a change to make when the pain is real.

## What this doesn't protect against

Anyone who reaches MOAD's private key can read every project's spend. That's the tradeoff you accepted by centralising: one key to guard instead of N, and one key whose compromise is total. Given the payload is aggregate token counts and dollar figures with no user data, I think that's the right trade, but it's worth naming rather than discovering later.

## 1. Generate the pair, once, on a trusted machine

Run this yourself rather than having me do it, so the private key never touches a transcript:

```bash
! openssl genpkey -algorithm ed25519 -out moad-private.pem && openssl pkey -in moad-private.pem -pubout -out moad-public.pem
```

Node equivalent if you'd rather not shell out to OpenSSL:

```js
const { publicKey, privateKey } = generateKeyPairSync('ed25519')
require('node:fs').writeFileSync('moad-public.pem', publicKey.export({ type: 'spki', format: 'pem' }))
require('node:fs').writeFileSync('moad-private.pem', privateKey.export({ type: 'pkcs8', format: 'pem' }))
```

No key size to choose. Ed25519 has exactly one, which is part of why it was the right pick.

## 2. Verify the pair before you rely on it

A mismatched pair 401s every project and looks like a dozen other bugs. Thirty seconds now saves an afternoon:

```js
// verify-pair.mjs — signs and verifies using createMoadRoute's exact payload format
import { readFileSync } from 'node:fs'
import { createPrivateKey, createPublicKey, sign, verify } from 'node:crypto'

const priv = createPrivateKey(readFileSync(process.argv[2], 'utf8'))
const pub = createPublicKey(readFileSync(process.argv[3], 'utf8'))
const payload = Buffer.from(`${Date.now()}:some-project-slug`)
const ok = verify(null, payload, pub, sign(null, payload, priv))
console.log(ok ? 'PAIR MATCHES — safe to commit the public half' : 'MISMATCH — do not use')
process.exit(ok ? 0 : 1)
```

```bash
! node verify-pair.mjs moad-private.pem moad-public.pem
```

I tested it both ways: matching pair prints `PAIR MATCHES`, mismatched pair prints `MISMATCH` and exits 1.

## 4. The private half goes into MOAD's env, and nowhere else

This is the only real secret in the system. Never Slack it, never put it in a ticket, never let it near a repo.

The practical snag is that a PEM is multi-line. Vercel accepts multi-line values if you paste directly into the dashboard, but base64 is more robust across every host and CI system:


```ts

)

export function moadSignature(projectSlug: string) {
  const timestamp = Date.now()
  return `${timestamp}.${sign(null, Buffer.from(`${timestamp}:${projectSlug}`), privateKey).toString('base64url')}`
}
```

## The failure mode to know about

Nothing validates the slug. A typo, a case difference, `8x_brands` vs `8x-brands`, a rename in one place and not the other — all of it surfaces as a flat 401, identical to a missing key or an expired signature. So when a project stops reporting, check that the two strings match before you go looking at the crypto. It's the likeliest cause by a wide margin.

The slug itself is arbitrary. Repo name is the obvious choice since it's already unique and nobody has to invent a convention.

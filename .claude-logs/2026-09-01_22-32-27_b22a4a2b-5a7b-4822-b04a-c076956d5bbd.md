Plan written to `code/documents/web-template-rbac-feature-flags-plan.md`. Here's the shape of it.

## The reference
- **RBAC** — model on `8x-brands/src/lib/rbac/` (it's mature): the winning ideas are **role = a small Prisma enum, permissions = a `text[]` grant list** (so adding a capability never needs a migration), a **wildcard top tier** (a new permission can never lock admins out), and a `cache()`'d per-request context gate. I genericize brands' domain-specific catalog into a small illustrative one.
- **Feature flags** — greenfield (neither brands nor core has it), so I designed it as an **extensible provider-agnostic resolution chain**, not a hard PostHog dependency.

## Part 1 — RBAC
- `prisma/schema/authz.prisma`: `Role` enum (`admin`=wildcard / `member` / `viewer`) + `role` on the user model.
- `src/lib/rbac/{permissions,roles,context}.ts`: catalog (read/write/dangerous kinds), role→permission map, and a `cache()`'d `getAuthContext()` with `requireUser` / `requireRole` / `requirePermission` throwing `AppError` (which the existing route/action factories already translate to the right status).
- **Wire an `authorize` option into `createApiRoute` + `validatedAction`** so gating is declarative and un-forgettable — same reason the factories already own Zod + error capture.
- Client: server-seeded `<AuthzProvider>` + `<Can permission>` (no client fetch → no waterfall).
- **RLS** goes in via the one sanctioned `prisma migrate dev --create-only` exception (Prisma schema can't express policies).

## Part 2 — Feature flags (extensible)
- `src/lib/flags/flags.ts`: typed registry, closed set of keys, each with a `kind` (`release` / `ops` kill-switch / `experiment` / `module` / `permission`). The `module` kind is the meeting's "toggle payments/messaging on/off" idea.
- `src/lib/flags/provider.ts`: `FlagProvider` interface + a precedence chain — **DB override → DB flag → PostHog → static default** — each provider optional. Adding LaunchDarkly/env/etc. = implement the interface. That's the "extensible."
- Server `getFlag`/`getAllFlags` (`cache()`'d, one query), client `<Feature>` seeded from a server snapshot.
- DB models (`FeatureFlag` + `FeatureFlagOverride`) are the optional third slice.

## Suggested sequencing
1. **RBAC core** ← recommend first; it ships the `requireUser`/auth-context layer that the template doesn't have today and that both systems need.
2. Feature-flags core (static + PostHog).
3. DB-backed flags + `flags.manage`-gated admin toggle.

**What it is**

`prisma/deploy.sql` is one hand-written file that runs on every push to `main`, right after `prisma migrate deploy` and before the zero-drift check, in the existing production job. Migrations record what changed once. This file holds what must be true after every deploy: extensions, views, functions, triggers, grants, reference-data upserts.

**The contract is idempotency, and CI proves it.** The `migrations` job in CI now applies the file twice to its throwaway Postgres. A statement that only works once fails there instead of on main. Two different paths, depending on whether the SQL should run every deploy or exactly once.

**SQL that must hold after every deploy** (extensions, views, functions, triggers, grants, reference-data upserts):

1. Add the statements to `prisma/deploy.sql` in the project. Every statement must be idempotent, so `CREATE EXTENSION IF NOT EXISTS`, `CREATE OR REPLACE`, `DROP ... IF EXISTS` then `CREATE`, `INSERT ... ON CONFLICT`.
2. Open a PR. CI replays the migrations onto a throwaway Postgres, runs your file twice, then drift-checks. A statement that only works once, or one that creates a table the schema doesn't declare, goes red there.
3. Merge to `main`. The Deploy migrations workflow applies the migrations, then the file, to production. That needs the `production-database` GitHub environment with `PRODUCTION_DATABASE_URL` set, which the project already needs for migrations. Nothing else to configure.
4. Locally, run it against your `.env.local` database:

```bash
pnpm exec prisma migrate deploy
pnpm db:deploy-sql
```

For a shared staging database:

```bash
node scripts/run-deploy-sql.mjs --db-url "$STAGING_DATABASE_URL"
```

The `staging-migration` skill does this for you after it reconciles staging.

**SQL that should run exactly once** (a backfill, a data fix):

The deploy file is the wrong tool, since it re-runs forever. Use a data-only migration instead. Against a local database:

```bash
pnpm exec prisma migrate dev --create-only --name backfill_plan_ids
```

Write the SQL into the generated `migration.sql`, then PR it like any other change. Prisma records it in `_prisma_migrations`, so it runs once per environment and production picks it up on merge. This is the sanctioned exception to "never hand-write a migration" in `docs/rules/migrations.md`. The alternative for a fix that needs application logic is a reviewed script using the app's own Prisma client, run by hand.

**Read-only inspection** stays as it was: the `sql-preview` skill, or `psql` with a `SELECT`. Writes through a SQL editor against staging or production are never allowed, and this branch doesn't change that.

Not quite. As built, `prisma/deploy.sql` is a standing list, not a scratch pad. Whatever is in it runs on every deploy, so you add a line when a new invariant appears and remove it only when that invariant goes away. Think of `CREATE EXTENSION IF NOT EXISTS`, a view definition, a grant. Those stay in the file for the life of the project.

If you treat it as a scratch pad and replace the contents each time, here is what happens:

- The SQL runs on every deploy until you replace it, not once. A fix like `UPDATE users SET plan = 'free' WHERE plan IS NULL` would keep re-applying to newly null rows for weeks.
- CI runs the file twice, so anything that only works once, like a plain `INSERT`, fails the PR. Anything that happens to be idempotent passes, and then re-runs forever.

So for the fermion-style one-off (write a fix, it runs once on deploy, next time you write a different one) the file is the wrong shape. Today the run-once path is a data-only migration, which Prisma applies exactly once per environment because it tracks it in `_prisma_migrations`. That works but it isn't as frictionless as "write SQL in a file".

If the replace-each-time model is what you actually want, two ways to get it:

1. **Recommended: a helper that makes a one-off feel like a scratch file.** `pnpm db:once backfill_plan_ids` creates a timestamped, empty `migration.sql`, you write the SQL, open the PR, and it runs once in production on merge. Prisma's own ledger tracks it, the drift check is unaffected, and every past one-off stays in the repo in order. The `local-review` skill would get a carve-out for data-only migrations.
2. **Literal scratch file, `prisma/once.sql`.** The runner hashes the file, keeps a small ledger table of applied hashes, and runs the content only when the hash is new. Replace the content, it runs once more. This needs a second ledger next to Prisma's, a ledger table that the drift check has to ignore, and a runner that can read query results, so it is more machinery for the same outcome.

Either one sits beside `deploy.sql`, which stays for the standing invariants. Tell me which you want and I'll build it on this branch.

Here it is, plainly.

**The file: `prisma/deploy.sql`.** Open it, write your SQL under the comment header, save. Example:

```sql
CREATE EXTENSION IF NOT EXISTS "pg_trgm";

CREATE OR REPLACE VIEW "active_admins" AS
  SELECT "userId" FROM "admin_members" WHERE "isActive";
```

**How it gets executed, three places, no action from you beyond the PR:**

1. **Your machine.** Run `pnpm db:deploy-sql`. That calls `scripts/run-deploy-sql.mjs`, which hands the file to `prisma db execute` against the database in your `.env.local`.
2. **Your PR.** CI's `migrations` job spins up a fresh Postgres, replays all migrations, then runs the same script on your file twice. If either pass fails, the PR goes red.
3. **Production.** When the PR merges to `main`, the `Deploy migrations` workflow runs `prisma migrate deploy` and then the same script against `PRODUCTION_DATABASE_URL`. Your SQL is now applied in production.

The one rule: the SQL must be safe to run repeatedly, because steps 2 and 3 run it again on every future PR and deploy. Use `IF NOT EXISTS`, `CREATE OR REPLACE`, `ON CONFLICT`. Lines you write stay in the file until you delete them.

**If the SQL is a one-time fix**, like a data backfill you never want to run twice, don't put it in that file. Write it as a migration instead:

```bash
pnpm exec prisma migrate dev --create-only --name backfill_plan_ids
```

That creates `prisma/schema/migrations/<timestamp>_backfill_plan_ids/migration.sql`. Write your SQL in it, open the PR. Steps 2 and 3 above apply it too, through `prisma migrate deploy`, and Prisma records it so it runs exactly once per database and never again.

So: standing SQL goes in `prisma/deploy.sql`, one-time SQL goes in a migration file, and the same PR-to-main pipeline executes both.

From a developer's seat, in a project built from this template, here is the whole thing.

**1. Write the SQL.** Open `prisma/run-once.sql` and replace whatever is below the comment header with the change you want:

```sql
UPDATE "plans" SET "seat_limit" = 6 WHERE "id" = 'team';
INSERT INTO "plans" ("id", "name") VALUES ('starter', 'Starter'), ('scale', 'Scale');
```

If the file already holds last week's one-off, delete it. It already ran.

**2. Try it locally.**

```bash
pnpm db:run-once
```

This runs the file against the database in your `.env.local`. Run it again and it says "already applied". That's the ledger working.

**3. Open the PR.** CI replays the migrations onto a fresh database and runs your file against it. If your SQL is broken, or needs rows that only production has, the PR goes red here, before it can touch anything real.

**4. Merge.** On the push to `main`, the deploy job applies the migrations, then applies your file to production once, and records its hash in the `_run_once_sql` table. Every deploy after that sees the hash and skips it.

**5. Next time**, go back to step 1 and replace the content. New SQL means a new hash, so it runs once, and the old one stays skipped.

Two things that trip people up:

- A comment-only edit doesn't count as new SQL. To rerun the same statements on purpose, change a statement.
- If you get a merge conflict in this file, keep only your SQL. The other person's already ran.

To see what has run on a given database and when:

```sql
SELECT left(hash, 12), applied_at, sql FROM "_run_once_sql" ORDER BY applied_at;
```

## What this repo actually is

Not an application. It's the **starter template every new 8x web project gets copied from** (GitHub template repo, not fork, not clone). The product isn't the ~2,900 lines of `src/` code, it's the set of conventions plus the machinery that enforces them. The app itself is deliberately near-empty: one home page, one analytics demo page marked "delete me", one smoke test.

Three layers, and they're tightly coupled:

1. **Rules** (`AGENTS.md` → `docs/rules/*.md`, 13 files, ~7k words)
2. **Enforcement** (ESLint rules, `scripts/*.mjs`, CI jobs, Zod schemas)
3. **A working reference implementation** of each rule in `src/`

Almost every rule has an actual mechanism behind it, which is what makes this different from the usual CLAUDE.md nobody reads. Examples: "no `any`" is an ESLint error; "logger is server-only" is a `no-restricted-syntax` selector matching `'use client'` files that import it; "env vars must be declared" is `pnpm check:env` walking `src/` for `process.env.X` and diffing against both `.env.example` and `src/lib/env.ts`; "never hand-write a migration" is a CI job that writes them for you.

## Stack

Next.js 16 App Router (Turbopack, React Compiler at `panicThreshold: 'all_errors'`, so a compiler bailout fails the build) + React 19, Tailwind v4 CSS-first, Prisma 6 on Postgres/Supabase, Supabase Auth, TanStack Query, next-intl, Sentry + PostHog, pnpm. Node 22, `node --test` for unit, Playwright for e2e.

## Request path, end to end

```
request
  → src/proxy.ts        Supabase session refresh, then next-intl locale routing
  → src/app/[locale]/layout.tsx
        AnalyticsProvider · NextIntlClientProvider · QueryProvider · Toaster
  → page (Server Component by default)
        data via @/server/db/client (Prisma, the ONLY file touching PrismaClient)
        who-you-are via @/lib/supabase/server (auth only, never data)
```

`proxy.ts` is worth reading closely: it runs Supabase **first**, then copies the whole cookie objects (options included, not just name/value) onto next-intl's response, because the ordering and the options both matter and both were bugs somewhere. The `supabase.auth.getUser()` call is wrapped in a bare try/catch to fail open, so a landing-page clone with placeholder keys still serves pages.

## The two hard architectural lines

**Prisma owns data, Supabase owns auth.** Supabase Data API stays off; RLS on with *no policies* on every user-scoped table as a deny-by-default lock (never `FORCE`, since Prisma connects as table owner). Authorization is enforced in the API/action layer, not the database, because Prisma bypasses PostgREST entirely. `User.id` **is** the Supabase auth uuid, set explicitly, never `@default(cuid())`.

**Sentry vs logger vs analytics, three distinct jobs.** Sentry = unexpected exceptions someone gets paged for. Logger (`src/server/lib/logger/`) = the structured record of what happened, JSON lines to stdout, correlation via `AsyncLocalStorage`, with `redact.ts` as a backstop that scrubs by key name *and* by value (URL credentials, `?api_key=`, bearer tokens, emails). PostHog = product behavior. `console.*` is banned in `src/`.

## The error funnel

Everything routes through one classifier:

```
normalize-error.ts  (pure, no SDK imports, shared by both sides)
   ├── capture-error.ts        server: Sentry + Slack + PostHog
   └── capture-client-error.ts client: Sentry + posthog-js
```

`AppError` means "the user caused this" (declined card, taken username). It carries a `userMessage` written for a human, gets returned straight through, and **skips Sentry entirely** because a guard rail doing its job isn't a bug. Everything else gets a generic message out front and full detail to Sentry.

The two entry-point wrappers are the same idea in two shapes: `createApiRoute` (Zod in, `NextResponse` out) and `validatedAction` (Zod in, `{ ok: true | false }` out). Both call `unstable_rethrow` or handle `ZodError` before reporting. `validatedAction`'s `unstable_rethrow` is load-bearing: without it a post-mutation `redirect()` silently becomes a failed result instead of navigating.

Four boundaries stack: `global-error.tsx` (inline styles and hardcoded hex, because globals.css may not have loaded, the one sanctioned exception to the token rule) → `[locale]/error.tsx` → `<ErrorBoundary>` for a smaller blast radius → `toast()` for recoverable ones. ChunkLoadError after a redeploy is intercepted at every boundary and reload-once-throttled instead of being reported.

## The migration workflow

This is the piece the README calls "the org's biggest unsettled debate," and it's inverted from what you'd expect. **You edit `prisma/schema/*.prisma`. CI writes the migration file and commits it back to your branch.**

The CI job replays committed migrations onto a throwaway Postgres 16 service container, then `prisma migrate diff` between "replayed history" and "current schema" *is* the missing migration. `scripts/generate-migration.mjs` refuses to write anything matching a destructive pattern (`DROP TABLE`, `SET NOT NULL`, type changes), which is the one time a human hand-writes SQL. After writing it, the script replays it to prove it applies.

Two details that were clearly learned the hard way and are documented in-line: `HEAD_REF` crosses into the shell as an env var and never as `${{ }}`, because that job holds `contents: write` plus the migrations token and refnames can contain backticks. And the token falls through App-install → `MIGRATIONS_TOKEN` PAT → `GITHUB_TOKEN`, where only the first two make the bot's commit trigger its own CI run, so a green PR under `GITHUB_TOKEN` is a false signal.

`deploy-migrations.yml` skips on `github.event.created` (the template-generation push, when the prod DB doesn't exist yet) but hard-fails on an empty `PRODUCTION_DATABASE_URL` at any later point. The comment explicitly calls out why those two are different facts.

## Analytics

The most opinionated subsystem. `src/lib/analytics/events.ts` is a typed taxonomy where the key set of `EventProps` **is** the allowed event set, so an off-list name or property is a compile error. ## Yes, mostly, with one hard limit

No provider publishes a machine-readable pricing endpoint. Not Anthropic, not OpenAI, not Google. Pricing lives on marketing pages. So "fetch the true price from the provider at runtime" doesn't exist as an option, and any design that assumes it will break.

What you can do instead is make the price a *dated fact in your own database* that a robot keeps fresh and a human approves.

## Your schema already solved the hard half

There's no `cost` column in that table, and that's the right call. Store tokens, compute dollars at read time. That single decision means a price correction never requires rewriting history, because you never wrote a dollar figure down in the first place.

What's missing is the other table: `ai_model_pricing`, keyed on `(provider, model, service_tier)`, with four absolute rates (input, output, cache_write, cache_read) plus `effective_from` / `effective_to`. Cost becomes a view joining `ai_usage.created_at` into the price row that was live at that moment.

Two things I'd insist on there:

**Effective-dated, append-only.** If you update prices in place, last quarter's report silently changes the next time someone runs it. That's the failure mode that makes finance stop trusting the dashboard.

**Absolute rates per tier, not a base price with multipliers.** Tempting to store one price and do `batch = 0.5x`, but it doesn't hold. Anthropic's fast mode on Opus 5 is $10/$50 against standard's $5/$25, which is its own rate card, not a multiplier on a base. Make `service_tier` part of the key and store real numbers.

## Where the rows come from

OpenRouter's `/api/v1/models` is the practical feed. Free, no auth, covers all three providers, includes cache read/write rates for many models. Three caveats:

- Their slugs aren't provider model ids (`anthropic/claude-opus-5` vs whatever the API actually returns in `response.model`). You need a mapping table, and it needs a loud failure when an unmapped model shows up rather than a silent zero.
- The prices are OpenRouter's. They track list price closely but aren't authoritative for what lands on your invoice.
- They don't model batch tier at all. Batch and fast rows stay locally maintained no matter what.

The fetch should be **a weekly CI job that diffs and opens a PR**, not a runtime call. Same shape as this repo's migration workflow: robot writes it, human reviews the diff, git holds the audit trail. A runtime fetch puts a network dependency in a money path and lets a bad upstream value rewrite your numbers with nobody noticing.

## The part that's genuinely unsolved

"Don't update everywhere" is a cross-repo problem, not a schema problem. Every project generated from this template gets its own copy and drifts independently. Options are a small internal package shipping the JSON, or one service owning the table and the rest querying it. I wouldn't build either yet. Ship the fetcher plus committed JSON in the template, and promote it once three repos actually feel the pain.

## Things worth deciding before you build

- **Cache write TTL.** Anthropic prices 5-minute and 1-hour cache writes differently (1.25x vs 2x input). One `cache_write_tokens` column can't tell them apart, and on a cache-heavy workload that's a real gap. Either split the column or put the TTL in `meta`.

Three separate questions, and you're right on the first one.

## Current rate is fine, and it's safe to start there

I over-engineered that. Existing model ids rarely get repriced. When pricing changes, it usually arrives as a *new* model id, and a new id gets a new row anyway. So for most of your history, current-rate and historical-rate produce identical numbers.

The thing that makes "current rate only" safe rather than risky: **the pricing file is committed to git.** If you ever do need "what did this cost at the time," you can reconstruct it by reading the file at that commit and backfilling. You lose nothing by starting simple.

So: one row per `(provider, model, service_tier)`, overwritten on change. If you want cheap insurance, add an `effective_from` column and have the sync append instead of update. Costs you two columns and the query becomes "latest row per key." But it's optional, not the thing to argue about.

The one rule I'd actually hold: **don't write a `cost` column into `ai_usage`.** Your schema already doesn't. Keep it that way. As long as cost is derived, every decision above stays reversible.

## Storing pricing in the DB was what I meant

I was proposing exactly that, a second table. Sorry if that read as the opposite.

The real question is **who needs to compute cost.** If you'll ever open Supabase's SQL editor, point Metabase at it, or write a raw analytics query, pricing has to be in Postgres so it can join. If cost only ever appears through your own app's API, a committed TS/JSON constant is less machinery and you skip the table entirely.

Given you're doing per-feature and per-brand attribution, I'd bet on someone eventually querying this in SQL. So: JSON in git is the source of truth, a small table mirrors it, a seed script pushes JSON into the table on deploy. Change the file, CI syncs the table.

## OpenRouter gives rates, not costs, unless you route through them

Two very different answers here.

**If you call Anthropic and OpenAI directly** (which your schema implies, since `service_tier: standard | fast | batch` are direct-provider concepts), then `/api/v1/models` gives you a rate card and you do the multiplication yourself. One footgun: the prices come back as strings in **dollars per token**, so you'll see values like `"0.000005"`, not `5.00` per million. Easy place to be off by 1,000,000.

**If you actually route traffic through OpenRouter**, the problem disappears entirely. Their generation endpoint returns the real cost of each call, already computed, with the model that actually served it. No pricing table, no sync job, no mapping, no drift. You'd store `cost` directly because it came from the horse's mouth.

That's genuinely the laziest possible answer, so it's worth asking out loud: **are you calling providers directly, or are you open to going through OpenRouter?**

The catch is that routing through them costs you the provider-specific features. Anthropic's batch tier at 50% off, cache TTL control, fast mode. Your `service_tier` column suggests you want those, in which case direct calls it is, and you're back to syncing a rate card.

So which is it? If direct, the design I sketched holds and I'd simplify it to current-rate-only. If you're flexible on routing, the whole subsystem might not need to exist.

## Go with the package

Your instinct is right, but I'd reweight both concerns.

**Row volume shouldn't be in the decision.** A usage row is a couple hundred bytes. Even at 100k calls a day that's ~36M rows and single-digit GB a year, which Postgres handles with an index and eventually monthly partitioning. Don't let that steer an architecture decision.

**Compute is a real concern, but it's about shape, not volume.** One blocking POST per completion is the bad version. Buffer in-process, flush on a short interval or batch size, never block or fail the caller. This template already has exactly that idiom in `src/lib/notifications/slack.ts`: fire-and-forget, `.catch(() => {})`, with the comment that alerting a human about a bug must never become a second bug. Same rule applies. Usage tracking can't break the feature it's measuring.

**And the strongest argument for the package isn't the one you made.** Fewer breaking points is true but secondary. The real one: "what is 8x spending on AI this month, by project and by feature" is a single SELECT if MOAD owns the table, and unanswerable in the per-project version without querying N databases and reconciling N pricing tables. That question gets asked eventually. Probably by someone who signs cheques.

## The one real cost of centralizing

Your `meta` holds `brand_id`, `campaign_id`, `user_id`. Those are foreign keys into the *project's* database, not MOAD's. So "AI spend for brand X" means MOAD either knows what a brand is, or ships ids back for the project to join. In the per-project version that join is free and local.

That's a genuine loss, and it's the only argument for Option B I find convincing. If it bites, the fix is a package that owns the client and the shipping, MOAD that owns the rows and pricing, and an opt-in local mirror for projects that need the join. Don't build that now, just know it's the escape hatch.

## Something both options miss

Your four token columns can't represent per-call charges. Server-side tools bill per invocation, not per token. OpenRouter's feed even carries a separate `web_search` price. The moment a project uses web search or code execution, a token-only table silently under-reports.

Worth adding a `tool_calls jsonb` or a couple of counter columns before this ships, whichever way you go. And it's a decent illustration of your own argument: that's one fix in a package versus five in five repos.

Also decide the failure mode now. If the POST to MOAD fails, drop or retry? Silent drops mean cost numbers quietly under-report, which for a billing system is worse than a loud error. Buffer with retry, plus a dropped-events counter so you know when the data is incomplete.

`eslint.config.mjs` blocks `'use client'` files from importing the logger via `no-restricted-syntax`, and `no-console` is scoped to `src/` but not `scripts/`. Same idea here, but `no-restricted-imports` is the simpler rule for this:

- ban `@anthropic-ai/sdk`, `openai`, `@google/genai` across `src/**`
- override that for the one wrapper file so it's the only place allowed to import them

That's about 15 lines in the existing config, no custom script. The error message can point at the wrapper, so someone who tries gets told where to go instead of just getting yelled at.

What it won't catch:
- dynamic `await import()` with a computed string
- someone hand-rolling `fetch('https://api.anthropic.com/v1/messages')`

You can add a `no-restricted-syntax` rule for a literal `api.anthropic.com` string if you care, but that's fairly deep into diminishing returns. The lint rule stops the accidental case, which is the one that actually happens.

**The "does it record correctly" half is a different problem.** Lint proves people go through the wrapper. It can't prove the wrapper works.

The deterministic code is `scripts/check-standards.mjs`, run as `pnpm check:standards`. It answers one question with no network, no model, and the same result on every run: is every engineering standard actually wired into this repo, not just written down? It exits 0 when all 19 checks pass and 1 with a named failure otherwise, so CI can gate on it.

## What it checks, and how each check decides

**Agent instructions.** It reads `AGENTS.md` and requires an "Engineering rules" heading. It extracts every `docs/rules/*.md` reference from that file and confirms each one exists on disk. It then does the reverse: lists every file in `docs/rules/` and confirms each is referenced from `AGENTS.md`, so a rule nobody is pointed at fails. It requires the six stack-agnostic core rules to exist by name. It reads `CLAUDE.md` and requires a line that is exactly `@AGENTS.md`, and applies the same test to the Gemini, Qwen, and Cursor files if they exist, so per-tool files import the rules instead of restating them.

**Commit discipline.** It stats the hook file for the executable bit, then asks git for the file's index mode and requires `100755`, because the index mode is what a fresh clone receives. It reads the hook and requires it to invoke the shared commit-message script, and requires that script to exist. It parses `package.json` and requires the `prepare` script to set the git hooks path. It reads the CI workflow and requires the commit-message script to run with a commit range.

**Gates.** It parses `package.json` and requires the seven gate scripts, and requires the lint script to fail on warnings. It reads the CI workflow, strips comments, requires a `pull_request` trigger, and extracts every package-script invocation with a regex that accepts pnpm, npm, yarn, and bun forms. Each gate must appear. It applies the same extraction to the fenced command blocks in the local-review skill only, so a prose mention of a command does not count as running it. For ESLint it does not grep the config file. It runs the installed ESLint with `--print-config` on the env schema file and reads the resolved rule severities, so a later flat-config block that switches a rule off is caught. For TypeScript it runs `tsc --showConfig` and reads the resolved `strict` value, so an extends chain cannot hide it. It requires a Prettier config and ignore file to exist.

**Environment.** It requires the env schema file to import zod, the example env file to exist, the env check script to exist, and the `check:env` script to invoke it.

**Repository hygiene.** It asks git directly with `check-ignore` whether a list of hypothetical machine-local paths would be ignored, probing each at the root and nested. That catches a pattern that only matches at the top level before it lets a nested file through. It lists tracked files with `ls-files` and fails if any match `.vercel/`, Supabase CLI state, `node_modules/`, `.DS_Store`, or a populated env file. It requires the session-log directory to exist, to not be ignored, to have at least one tracked file, and to be listed in the Prettier ignore file.

## How the code is built

- Every check is an object with an id, a title, and a run function that returns pass or fail with a detail string. A shared context gives each check the repo root, file readers, a git runner, the tracked-file list, and the parsed `package.json`.
- Every text scan asserts it found something before judging what it found. An `AGENTS.md` with zero links fails rather than trivially passing. A workflow that invokes no scripts fails. A repo with zero tracked files fails. This guards against the app-discovery trap where a check passed for weeks by matching nothing.
- Git is used as the oracle for anything git owns: ignore rules, tracked files, index modes. The tools are used as the oracle for their own config. Missing tools and non-git directories are reported as failures, never skipped.
- Three modes: bare for this repo, `--root` to audit another checkout, and `--json` for machine consumption.

## How it is proven

The test file builds a throwaway git-initialised fixture copied from the template, confirms the fixture passes everything, then breaks one standard per test and asserts the specific check fails and names the cause. Thirty cases cover missing, dangling, and orphan rules, a hook that is executable locally but not in the index, a gate removed from CI, a gate surviving only in a YAML comment, an override block flipping the ESLint rule off, nested tracked `.vercel/`, root-anchored ignore patterns, and the JSON exit path.

It does not check stack conventions like Prisma-only data access or Server Component boundaries, whether the gates pass, or anything living in GitHub or Vercel settings. Those need the code read or a human, and `docs/STANDARDS.md` says so.

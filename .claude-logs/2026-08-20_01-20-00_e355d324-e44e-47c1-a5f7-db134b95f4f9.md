Good, and genuinely surprising: **neither `8x-brands` nor `8x-core` uses Radix, `cva`, or a shadcn-style component library at all.** No `Button` component exists in either repo. Their actual pattern is different from what I built:

- **Exported Tailwind class-string constants, not components** — `PRIMARY_BUTTON_CLASS`, `INPUT_CLASS`, `LABEL_CLASS` (from `8x-core/src/components/admin-ui/form.ts`), applied directly to native `<button>`/`<input>` elements. No wrapper component for pure styling.
- **Scoped per surface, not shared globally** — `8x-core` has *three separate* class-constant sets (`admin-ui/form.ts`, `creator-ui/form.ts`, `brand-ui/`), each deliberately different (the admin buttons are `rounded-xl`, the creator-portal ones are `rounded-full` pills) because those are visually distinct products sharing one codebase, not one design system.
- **Components only exist when there's real behavior** — `SignInSubmitButton` wraps `useFormStatus` for a pending state; that's it. Named for what they do, never a generic `<Button variant="primary">`.
- **Toast/Select are hand-rolled, not Radix** — `8x-brands`' `ToastProvider` is ~35 lines of plain Context + `useState` + `setTimeout`, single-slot with replace semantics (a new toast swaps the message, no queue), `role="status" aria-live="polite"` for accessibility instead of a library.

My read: this is a **multi-surface product's** answer to the same problem, not necessarily a better one for a starter template. `8x-core`/`8x-brands` hand-roll because they have 2-3 genuinely different visual languages (admin vs. creator-portal vs. brand) sharing one repo — a shared `Button` component with variants would fight that. A single-surface template benefits more from actual reusable components (polymorphism via `asChild`, one place to fix a focus bug) than from class-string constants duplicated per surface. And Radix's Toast is doing real accessibility work (focus management, portal, proper live-region timing) that their hand-rolled 35-line version doesn't attempt.

I'd leave what's built as-is — it's the more portable default for a template that doesn't yet know if it'll have one surface or three. Worth documenting the class-constants-per-surface pattern in `docs/rules/components.md` as the recommended escalation *if* a project grows multiple visual surfaces, rather than adopting it now. Want me to add that note, or leave it and move on?

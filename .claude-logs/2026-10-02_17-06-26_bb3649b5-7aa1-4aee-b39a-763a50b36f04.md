## Step 1: What the code does today

**How clips and edits are modelled**
- `SourceRange = { startSeconds, endSeconds }` and `Clip = { id, ranges }` (`sequence.ts:9-10`). A range has no "which file" field, so it always means the uploaded file.
- `Edit = { trim, cuts }` (`cleanup.ts:18`).
- All state is React `useState` in `video-editor.tsx` (`trim`, `cuts`, `clips`, `undoEdit`). Nothing goes to the database; the only Prisma table this feature touches is `ai_usage`.
- Undo is a single slot, `undoEdit: Edit | null` (`video-editor.tsx:63`). Clean-up and the filler cut share it, and it covers trim and cuts only, not clips.
- **So a clip can't come from another file today.**

**How the timeline, playback and export play an edit**
- `playableSegments(clips, edit)` returns a list of ranges of the one file (`sequence.ts:121`).
- The timeline is drawn in the file's own time (0 to duration).
- `useSequencePlayback` moves the single `<video>` between segments by setting `currentTime`.
- `recordEdit(url, segments)` plays one offscreen video from one URL (`export-video.ts:68`). It pauses the recorder while it jumps between segments, so it would handle switching to a second video cleanly.
- **A replacement take doesn't fit unchanged.** The segment type, the playback hook, export, and the timeline's time-to-position mapping all need to change.

**What gap detection gives you to reuse** (`filler-cuts.ts`)
- `quietRuns(loudness, from, to)` finds every quiet stretch of at least 40 ms. It isn't exported yet.
- The search for the gap before the first word and after the last word sits inline in `planFillerCut`, along with checks that only make sense for a single filler (sound length 60 ms–1.2 s, "no gap inside it"). A sentence has gaps inside it, so those checks don't carry over; the gap search and the "cut at the middle of the gap" rule do.
- `measureLoudness` gives loudness in 10 ms steps with a quiet threshold fitted to each recording (`take-audio.ts:99`). It also already finds a typical speech level (the 90th percentile), which level matching can use.
- `decodeTakeAudio(file)` will decode a recorded blob, which also gives its real length. A browser recording otherwise reports its length as `Infinity`.

**What word timing is stored, and where**
- `Transcript = { words, segments }` (`transcript.ts`). Each word has text and start/end times from Deepgram nova-3, which keeps fillers.
- `segments` are the transcript lines, ended at `.`, `?` or `!`. Each line runs from its first word's start to its last word's end, so **a line is already a clickable sentence**.
- Both are held only in the browser's query cache (`['take-transcript', url]`); loudness is under `['take-audio', url]`. Nothing is persisted, and the panel's lines currently just jump the playhead (`transcript-panel.tsx:28`).

## Step 2: Proposed design

### Recording: audio only, or camera and mic

| | Audio only | Camera + mic (**recommended for v1**) |
|---|---|---|
| Picture under the new sound | Unsolved. The new take is never the same length as the original, so the original picture would have to be frozen, stretched or cut. Lips visibly don't match on talking-head video. | The new take brings its own picture, so there's no length or lip-sync problem. |
| Look of the result | No visual jump, but a visible lip mismatch. | A visible jump cut (framing or light may change). This is common and accepted in talking-head editing. |
| Build cost | Recording is simpler, but handling the picture is the hard part, and any choice there would be guesswork. | A second video in playback and export, and letterboxing when the camera's shape differs from the original. |
| Best for | Screen recordings (voice over a static screen) | To-camera takes |

I recommend camera + mic because it is the only option with no unsolved problem. Audio only for screen recordings is a later step and needs your decision on the picture (most likely: freeze the original's frame).

### Model changes
- Add `Replacement = { id, span, url, take, gain }`:
  - `span`: the original stretch it replaces.
  - `take`: the trimmed part of the recording that plays.
- Segments gain a source field: the original file, or a replacement's id.
- `playableSegments` skips the span and plays the take in its place.
- Rules, kept deliberately strict:
  - A span must sit inside one clip and inside the trim, and must not overlap a cut. Otherwise "Re-record" is disabled with the reason shown.
  - No split inside a replaced span.
- **Timeline:** the span is marked like a cut, with a "replaced" style. While the replacement plays, the playhead moves across the span in proportion.
- **Playback:** a second `<video>` sits on top of the main one. At the span it pauses the main video and plays the replacement, then hides it and carries on after the span.
- **Export:** draws from whichever video is active onto the existing canvas, letterboxed to the original's size. Each video's sound goes into the same audio mix.

### Choosing the splice points
- Search for a quiet gap just before the sentence's first word and just after its last word, using the gap search pulled out of `planFillerCut`. The filler code is unchanged, and its existing tests prove that.
- Cut at the middle of each gap, exactly like filler cuts. Gaps between sentences are usually long, so a gap is usually found.
- **If either side has no gap, the app doesn't guess.** "Re-record" is disabled with "No clean pause at the start/end of this sentence". Setting the edges by ear is a later step, reusing the filler cut editor's handles.
- The new take gets the same treatment: its leading and trailing silence (record-button click, breath) is trimmed, keeping a short pad that is held as a constant.

### Seam quality, simplest version first
- **Cut silence to silence.** The original is cut mid-gap and the new take keeps its own quiet pad, so each seam joins quiet to quiet. The same approach for filler cuts was checked by ear on `Cap.mp4` and sounded clean, with no fades.
- **No crossfade in v1.** I'd only add short (~10 ms) fade-out/fade-in ramps in export if a measured seam shows a click. Adding them without that would be speculative.
- **Level matching:** one gain value for the whole replacement. It is the speech level (90th percentile) of a few seconds of original around the span, minus the take's speech level, capped at ±12 dB. It's applied through a gain step in Web Audio, because a video element's own volume can only turn sound down, never up. That routes only the replacement video through Web Audio; the main video plays as it does now.
- **Room-tone risk:** browser noise suppression and automatic gain would make the new take's background sound different (a near-silent background against the original's room hiss). I'd record with those two turned off. I'm not certain that's right, so the seam measurements below decide it.

### Storage and Undo
- The recording is kept as an in-memory link to its file, like the uploaded video. It's lost on reload, like every other edit, and never leaves the browser. There is no AI cost: the new take isn't transcribed.
- The single Undo slot becomes `{ edit, replacements }`, so clean-up, filler cut and re-record share the same one-step Undo.
- Recordings are released when a new video is loaded or the editor closes. A recording dropped by Undo stays in memory until then (a sentence is about 1–2 MB). That is simpler than tracking which recordings are still referenced.
